# AviUtl2 功能对齐

AviUtl2（ExEdit2 2.1.16）不是"经典 AviUtl 加几个效果"，而是一次内部重写：
RGBA16F 与 PCM32F 精度、GPU 渲染、单窗口内自由分组，场景、对象、图层与效果
的关系都重新定义过。本页记录其中哪些能力被采纳、哪些没有，以及为什么——这样
同一片区域不必被反复评估。界面层面的对齐另见专门文档；本页讲的是编辑模型与
其背后的功能集。测量基线为 `8c1efccc`（0.7.0-rc.2）。

## 对照是如何做的

AviUtl2 的分析依赖四类证据，下文的每条结论都至少依据其中之一：

| 证据 | 来源 | 支撑了什么 |
| --- | --- | --- |
| 操作说明 | `aviutl2.txt` 的「簡易説明」章节 | 功能语义、交互细节、文档化的限制 |
| 外观配置 | `style.conf`、`system.conf` | 窗口度量与色彩 |
| 二进制宽字符串 | `.rdata`，文件偏移 `0x33d000`，大小 `0x1fda00` | 菜单项、命令名、设置项、组件名 |
| 官方文档 | <https://docs.aviutl2.jp/usage.md> 与 Lua 参考 | 窗口职责、`obj` 字段、脚本语义 |

没有为了推断算法而反编译任何函数。字符串与类名足以确定一个功能是什么、从哪里
进入、边界在哪里；实现细节只有在真正移植时才需要关心。

## 判断的含义

判断分四种。**保留**指本项目的做法已经更好；**采用**指值得照 AviUtl2 那样做；
**改造后采用**指能力值得要，但实现方式必须改；**不做**指不适合本项目。

| 能力 | AviUtl2 | 此前的 Freya NLE | 判断 |
| --- | --- | --- | --- |
| 内部精度 | RGBA16F、PCM32F | wgpu 管线，浮点合成 | 保留 |
| 场景操作进撤销栈 | 不支持 | 场景增删改都可撤销 | 保留 |
| 单窗口分组 | 有，可分离/合并/标签 | 多窗口 + 项目标签 + 合并工作区 | 保留 |
| 帧标记与备注 | 有，带列表与跳转 | 无 | 采用 |
| 图层设置（整层偏移与音量） | 有 | 无层偏移，只有对象级变换 | 采用 |
| 图层名与背景色 | 有 | 仅 `Layer N`，无背景色 | 采用 |
| 文本控制字符 | 完整一套 | 纯文本与对象参数 | 采用 |
| 参数参照式 | 跨效果、跨层，带函数 | 只有 `=` Lua 表达式（AviUtl 1.x 风格） | 改造后采用 |
| 效果级复制/剪切/粘贴 | 有，自身与自身及之后 | 只有对象剪贴板与效果排序 | 采用 |
| 逐项预设 | 有 | 效果级预设 | 改造后采用 |
| 新建/初始化默认值 | 有，可按媒体组合 | 无 | 采用 |
| `.object` 别名 | 有 | 无 | 不做——片段已覆盖大部分用途 |
| 对象列表 | 有 | 无 | 采用 |
| 对象分组 | 有 | 无 | 采用 |
| 场景标签与筛选 | 有，`\` 分层 | 无 | 采用 |
| 场景引用复制 | 有 | 场景对象，复制语义未核实 | 改造后采用 |
| 批量输出 | 有 | 单次导出带进度 | 采用 |
| 备份历史 | 间隔、上限、可恢复 | 只有崩溃恢复快照 | 改造后采用 |
| 菜单定义（顺序、层级、显隐） | 有，统一机制 | 固定菜单 | 不做——收益低、测试成本高 |
| 快捷键自定义 | 有 | 有，带冲突校验 | 保留 |
| 输入/输出插件优先级 | 有 | 走 FFmpeg，无插件表 | 不做 |
| 缓存大小设置 | 有 | 后端自管 | 不做——暴露给用户只会制造错误配置 |
| 高 DPI / GPU 选择 | 有 | 由平台与 wgpu 决定 | 不做 |
| 语言文件 `.aul2` | 有 | gettext `.po`（英/中/日） | 保留 |
| 字体与表情即放即用 | 有 | 系统字体，无表情注册 | 改造后采用 |
| 图片、视频、音频对象 | 有 | 有 | 保留 |
| 组控制、相机、帧缓冲、场景对象 | 有 | 有 | 保留 |
| 画像合成与部分滤镜 | 有 | 帧缓冲对象能合成下位图层，但层数、位置与控制归属不同 | 保留——不新增独立对象 |
| 剪辑对象与上层剪裁 | 有 | `clipping` 效果 + `clipByUpperObject` | 保留 |
| BPM 网格与吸附 | 有 | 有，场景级 BPM、细分、磁吸 | 保留 |
| 涟漪、滚动、滑移 | 无 | 有 | 保留 |

## 设计决定

### 采用

- **帧标记是场景数据，不是界面状态。** 随项目保存、随撤销回滚、按场景隔离。
  备注是标记的一部分。标记列表是导航入口，不是第二条时间线。
- **图层设置是图层属性。** 坐标与音量偏移作用于该层所有媒体对象；相机控制对象
  不受影响，与 AviUtl2 一致。图层名与背景色是同一份属性。
- **文本控制字符做成解析层。** 先做不影响时序的颜色、字号、字体、坐标与间距，
  再做需要逐帧求值的 `<w>`、`<c>`、`<r>`。
- **参照式复用表达式求值器。** 引用先解析成"当前帧的参数值"，再交给既有 Lua
  表达式路径，避免第二套求值语义。
- **批量输出是队列。** 每个条目携带项目路径、输出设置与覆盖策略；队列可暂停、
  取消、重排；渲染复用单次导出管线。
- **备份历史是显式的版本列表。** "每个项目保留 N 份、可手动打点"建立在既有恢复
  快照之上，恢复走既有打开路径，不引入第二种项目格式。

### 改造后采用

- **对象分组。** AviUtl2 的组是选择与移动的联合体；这里实现为组 ID 加组内对象
  集合，只影响选择、移动、删除的原子性，不改渲染顺序。
- **场景标签。** 保留 `\` 的分层与筛选，但标签存成数组而不是从字符串解析，界面
  再按层级折叠。
- **逐项预设。** 复用既有预设存储，把作用域从"效果"扩展到"效果项"。

### 不做

这些被排除是因为替代方案更差，而不是因为难：

- 全自绘控件与固定像素度量——无障碍与 DPI 处理会倒退。
- 一文档一窗口——项目标签更好。
- 让场景操作不进撤销栈——这是 AviUtl2 的已知短板。
- Windows 专属插件 ABI——本项目通过包与 Lua 扩展。
- 把缓存大小交给用户——后端自管，暴露只会制造错误配置。

## 仍未实现的部分

上表已经闭合，没有一行停在未分类状态。另有六项能力属于**已知缺口**而非决定，
当前判断是成本高于收益。列在这里，是为了让将来的尝试从理由开始。

| 能力 | 为什么仍然开着 |
| --- | --- |
| `obj.sx` / `obj.sy` / `obj.sz` | 文档注明 `zoom` 与 `aspect` 在新旧脚本格式下的"算出反映处理"不同，而 Qt 前端只有输出侧（`sx = baseScale * aspectX`），从来没有输入路径。渲染器有独立的 X/Y/Z 缩放，但它与 `zoom`、`aspect` 如何叠加没有定义；靠猜正是单位错误产生的方式 |
| `obj.effect()` / `obj.draw()` / `obj.setfont()` | 这组函数让脚本驱动绘制。文本脚本目前在排版**之前**运行，而这些调用要求它在绘制**之中**运行，需要重新设计脚本沙箱边界与渲染时机——不是补几个字段 |
| カメラ制御的光源 | 需要层平面法线、十路光源 uniform、漫反射与镜面项，以及阴影范围。这是渲染器级改造，而且没有 AviUtl2 对照就无法判断正确性 |
| `obj.w` / `obj.h` | 尺寸是排版结果，而脚本在排版前运行 |
| 拖动色块排序 | 纯打磨，成本高于价值 |
| 跨项目输出批次 | 单次导出与批量队列已覆盖主要用途；跨项目需要先定义"把不同工程并进一条队列"是什么意思 |

## 参与这一区域的工作

如果你要挑其中一项，**写明你依据的证据**，并照上面的方式记录。这个区域的风险不在
工作量，而在看似合理的猜测：一个错误的单位或猜错的叠加规则可以通过数百个测试，
同时产出肉眼可见的错误结果。`aspect` 就是警示——它作为百分比抵达合成器，而合成器
读的是比例，结果是每个对象被横向拉伸 101 倍，而整套测试仍然全绿。宁可用驱动真实
管线的测试，也不要用断言一个常量的测试。
